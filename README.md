# Explainable Early Diabetes Risk Prediction Using Clinical and Lifestyle Data with Personalized Risk Reduction Recommendations

Educational machine-learning prototype that scores **diabetes risk probability**, explains the score with **SHAP**, lets you run **what-if lifestyle simulations**, and shows **conservative, non-prescriptive** suggestions.

This is a **risk-screening / teaching tool**, not a diagnosis, prescription, or medical device.

## Problem Statement

Many student diabetes projects stop at a single accuracy number. Clinicians and users also need to know *why* a model scored a profile the way it did, which inputs matter, and how a *hypothetical* change in lifestyle-style fields would move the **model's** probability — without claiming that the same change would move a real person's medical risk by that amount.

## Motivation

A final-year B.Tech project should look like a small ML product: a preprocessing pipeline, several models compared fairly, a saved train/serve path, explainability, and a professional interface with honest limitations.

## Features

- Clinical-style + lifestyle/wearable-style inputs
- `sklearn` `Pipeline` + `ColumnTransformer` (no train/serve mismatch)
- Multiple models compared with stratified cross-validation
- Probability, educational risk category, and holdout metrics
- Global and individual SHAP explanations
- What-if simulator with current vs simulated predicted risk
- Personalized, conservative lifestyle notes (no medications)
- Streamlit dashboard with dedicated tabs

## Technologies Used

Python, Streamlit, scikit-learn, XGBoost (if installed), SHAP, pandas, NumPy, Plotly, Matplotlib, joblib

## Dataset

The file `data/diabetes.csv` is **synthetic demonstration data**, generated by `generate_dataset.py`.

- **Target:** `diabetes` (0/1)
- **Numeric clinical-style fields:** pregnancies, glucose, blood pressure, skin thickness, insulin, BMI, diabetes pedigree, age
- **Numeric lifestyle-style fields:** sleep hours, resting heart rate, daily steps, active minutes, HRV

There are **no categorical columns** in the current table. The preprocessor still has a categorical branch so extra wearable features can be added later.

### Pima Indians Diabetes dataset (not used as the training file)

This project does **not** train on the original Pima table. Pima is small, drawn from a specific population, uses `0` as a missing sentinel in several lab columns, contains **no** wearable signals, and cannot support claims of clinical accuracy. Column names here only *resemble* that schema so a real clinical extract could be swapped in later.

Possible leakage: the synthetic label is sampled from a known function of the features plus noise. That is a teaching design, not an EHR join leak. It also means metrics look **more optimistic** than on real messy data.

## Machine Learning Models

Trained and compared:

- Logistic Regression (baseline)
- Decision Tree
- Random Forest
- Gradient Boosting
- XGBoost (when the package imports)
- SVM (RBF, with probabilities)

**Selection** uses mean stratified 5-fold **ROC-AUC** on the training split (recall, then F1, as tie-breakers). Accuracy is reported but not used as the only criterion, because missing a high-risk case is costly in a screening setting.

Holdout metrics for the selected model are filled in after training (see **Results**).

## Explainable AI

SHAP describes how features **contributed to the model's prediction**. That is not proof that a feature causes diabetes.

## What-If Simulation

The What-If tab re-scores the **same trained model** on edited lifestyle fields and reports current vs simulated predicted probabilities. Language in the UI stresses that this is a hypothetical model scenario.

## Personalized Recommendations

Notes are generated from entered values (sleep, steps, activity, BMI, glucose, and so on). They are conservative and never include medication names or doses.

## Limitations

- Synthetic sample, constructed labels, optimistic metrics vs real clinics
- No demographic fairness study or external validation
- Educational probability bins, not diagnostic thresholds
- Wearable fields are typed in, not streamed from a device
- SHAP / KernelExplainer may be slow or unavailable for some estimators; the app should warn instead of crashing

## Future Improvements

- Larger, real, consented datasets
- Wearable sensor integration (steps, sleep, resting HR)
- Longitudinal (repeated) measurements
- External validation and calibration on local hospital data
- Fairness analysis across age and other groups
- Production model monitoring (data drift, prediction drift)

## Disclaimer

This repository is an **educational / research prototype** for academic demonstration. It is **not** a medical diagnostic tool and must not be used to make treatment decisions.
